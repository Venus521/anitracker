## 一、为什么这两个功能一直"做不好"（根因）

### 1.1 同步 —— 不是坏了，是每次卡 13 秒然后失败

实测确认：

| 测试项 | 结果 |
| --- | --- |
| `api.bgm.tv` 直连 | ❌ 10 秒超时（HTTP 000） |
| `api.bgm.tv` 走 Clash 7897 | ✅ 200 |
| 原公共 CORS 代理 `proxy.cors.sh` | ❌ 已失效 |
| 原公共 CORS 代理 `api.codetabs.com` | ❌ 已失效 |

原网络层逻辑：**先直连等 8 秒 → 失败再走两个已死的公共代理各 5 秒 → 全失败 → 报「网络不可达」**。
用户体感 = 每次点同步干等 13 秒，然后一句看不懂的报错。这就是 9/15「想瘦身」把 `BGMSYNC` 关掉的原因。

### 1.2 TV原创标注 —— 数据源只有 58 部老番

原数据集 `tracker-filler-data.js` 来自 `animefillerguide.com`（已停更），仅 58 部，且**不含柯南**——而柯南是用户正在追的。所以「批量补齐来源」注定大面积失败。

## 二、改了什么

### 2.1 网络层重做（index.html）

- **直连超时 13s → 4s**，失败立即给诊断，不再长时间空等
- **移除两个已死的公共 CORS 代理**
- **失败诊断改为可照做**：
  > 「无法连接 Bangumi。绝大多数情况是「代理没开」——请打开 Clash / 代理软件（并开启系统代理或 TUN 模式），然后重试。」
- **新增可选「CORS 中继」**（同步中心 → 高级设置 → 仅进阶用户自建反代时填）

> ⚠️ **重要认知修正**：初版曾实现「用户自填 HTTP 代理」，但**浏览器的 `fetch` 无法指定 HTTP 代理**（代理只能由浏览器/系统级接管）。实测确认该方案不可用，已改为上述正确方案。

### 2.2 TV原创标注数据源替换

- 数据源：`animefillerguide.com` → **`animefillerlist.com`**（覆盖广、在更新）
- **数据集 58 部 → 212 部（+265%）**，TV原创 3504 集 / 半原创 2610 集
- 分类映射：
  | 原站分类 | 本应用 |
  | --- | --- |
  | `Filler` | TV原创 |
  | `Mixed Canon/Filler` | 半原创 |
  | `Anime Canon` | 半原创 |
  | `Manga Canon` | 漫改（默认，不标记） |
- `FG_ALIAS` 别名表扩充至 80+ 条
- 新增 `fgLooseMatch`：中英文标题松散兜底匹配
- **命中示例**：柯南 575 集、死神 163 集、火影 90 集、海贼王 94 集、银魂 23 集

### 2.3 ★ 解决「以后新番怎么办」——三层机制

| 层级 | 机制 | 适用 |
| --- | --- | --- |
| 1 | **本地库**（212 部，零网络秒开） | 你追的老番长篇 |
| 2 | **联网实时抓**（`fgFetchSlug`/`fgParseAfl`） | 本地没有的新番：点一次即从 animefillerlist 抓取，并自动缓存到 `localStorage(at_fg_live)`，之后离线可用 |
| 3 | **手动标注**（原有功能） | 网上也没有的冷门/刚播新番 |

### 2.4 同步开关恢复

`BGMSYNC` 由 `false` → `true`，详情页「⟳ 拉取Bangumi进度」「↑ 推送Bangumi」按钮恢复。

## 五、遗留与建议

1. **数据集要不要定期更新**：`爬虫-animefillerlist.py` 已归档在本目录，以后想更新只需重跑一次（约 28 分钟，带缓存可断点续跑）。
2. **联网抓取的 CORS 限制**：浏览器直连 `animefillerlist.com` 可能被 CORS 拦。若遇到，可在设置里配 CORS 中继，或直接手动标注。
3. **备份目录已被清理**：本次工作期间有一个并发流程删除了 14 个 `backup_*` 与 3 个 `_rollback_drill*` 目录（符合「确认没用的直接删」要求）。历史版本在 git 中均可取回。
4. **`ani-tracker.html` 是 index.html 的同步副本**：改完 index.html 必须运行 `同步双入口.py`，否则回归测试 T00 会红。
