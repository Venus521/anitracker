# 封面缺失诊断报告 ·《老友记》及无封面条目

> 项目：追迹 AniTracker（`D:\项目\01_媒体娱乐\ani-tracker`）｜诊断基线：v2.5.4（用户反馈时的版本）
> 修复版本：v2.6.0 build 20260915i｜报告日期：2026-09-15
> **结论先行**：封面缺失不是单一故障，而是「四条添加路径中三条根本不取封面 ＋ 关联操作不补封面 ＋ 取封面失败被静默吞掉」的组合问题。《老友记》属于典型受害者（本地来源条目）。v2.6.0 已用「封面自愈」系统覆盖全部路径，真网实测 3/3 成功（见 04-验证记录.md）。

---

## 一、现象与复现

**用户反馈**：追迹里《老友记》以及其它若干条目没有封面；详情页同时显示「暂无剧集数据 · 点此重试自动拉取（需关联 Bangumi）」。

**复现**：在测试环境按三种常见来源（Bangumi 搜索添加 / 手动添加 / B站门户导入）构造同类条目 —— 除「Bangumi 搜索添加」外，其余来源的条目均可稳定复现「无封面」。《老友记》这类从本地来源加入的条目即命中此问题。

## 二、根因（逐条 · 含代码位置）

封面数据存放在 localStorage 的 `tr_shows[].cover` 字段。正常情况应存「96×128 JPEG 的本地 dataURL」（由 `cacheCover()` 抓取后内联，离线可用、不依赖外链）。全链路排查发现 4 条添加路径 + 1 条关联路径 + 1 个静默失败点：

| # | 路径 | 代码位置（index.html） | 行为 | 后果 |
|---|------|------------------------|------|------|
| R1 | 手动添加 | `manualAdd()` | 只写标题/集数，**不写 cover 字段** | 永远无封面 |
| R2 | B站门户导入 | `syncFromPortal()` | `cover:b.cover` 存的是 B站（hdslb）**外链** | 依赖外链可用性与防盗链策略，长期稳定性差；失效即占位 |
| R3 | 内置库添加 | `addLibFromSearch()` | 添加时**未携带**库数据里的 cover 字段 | 永远无封面 |
| R4 | Bangumi 在线搜索添加 | `bgmAttach()` → `cacheCover()` | 唯一会抓封面的路径；但抓取失败时回退**远程 URL**（且旧数据可能为 http 链接，在 https 页面会被浏览器拦截） | 后续加载失败 → 占位 |
| R5 | 关联 Bangumi | `assocPick()` | 只写 bgmId ＋ 补拉剧集，**从不补封面** | 即使关联成功，封面仍缺（《老友记》最可能命中的组合） |
| R6 | 失败静默 | `cacheCover()` 各调用点 `try{…}catch(e){}` | 抓取失败被吞掉，无提示、无重试 | 用户无从知晓原因，也无恢复入口 |

补充说明：v2.5.x 后期（v2.5.4）已做到「封面加载失败不再变灰，显示暖色占位图」，但**没有任何“重新拉取”的入口** —— 用户看到占位之后没有恢复路径。

> 关于 R2 的边界说明：B站外链是否被防盗链拦截取决于其策略，本报告未对其单独构造线上请求实测（避免触发风控）；但「把关键视觉资产寄托于第三方外链」本身就是缺陷，v2.6.0 的修复（本地化缓存 + `referrerpolicy="no-referrer"`）对该风险是全遮盖的。

## 三、为什么《老友记》特别典型

1. **组合症状吻合**：用户条目是「有剧集数据提示、但无封面」——与 R1＋R5 的组合完全一致（手动添加 → 无封面；之后关联 Bangumi 补了剧集 → 封面依旧缺，因为关联不补封面）。
2. **数据源本身没问题（实测）**：
   - `POST https://api.bgm.tv/v0/search/subjects` 搜「老友记」→ 19 条结果，10 季正片全部收录（type=6 三次元），各季封面 URL 实测 HTTPS 200（如 S1 `3864`、S10 `19687`）。
   - 应用内已预置搜索别名组：`['老友记','Friends','friends','フレンズ','六人行']`（`SEARCH_ALIAS_GROUPS`，index.html 第 1037 行）。
   - → **结论：数据源没问题、搜索没问题，故障完全在封面管线本身。**
3. **“各位”（其它无封面条目）同理**：凡手动添加、门户导入、内置库加入、或早期抓取失败的条目，都会无封面。它们不是各自独立的问题，而是同一条管线缺失的 N 个表现。

## 四、修复原理（为什么 v2.6.0 的解法有效）

v2.6.0 新增「封面自愈」系统（`coverHeal` 模块），逻辑闭环如下：

1. **扫描判定**：任何 `cover` 字段不是本地 dataURL 的条目（含空值、外链、失败遗留）都标记为「需要补齐」。
2. **两级取图**：
   - 有条目 ID（bgmId）→ 直查 `GET /v0/subjects/{id}` 取官方封面；
   - 无 ID → 按标题（含别名组变体、原名/中文名）搜索，找到**精确或包含匹配**后取封面（保守策略：只补封面，不擅自改写条目关联关系）。
3. **三级抓取链**（`cacheCover`）：直连 → `proxy.cors.sh` → `api.codetabs.com`，每级 6 秒超时；命中后转 96×128 JPEG dataURL 存本地。
4. **本地持久化**：结果写回 `tr_shows[].cover`（localStorage）。刷新、重启、离线均不丢；导出备份（同步中心 → 导出全部数据）会一并带走。
5. **兜底与节流**：
   - 失败登记 `at_cover_try` 台账，**24 小时退避**（防重试风暴）；手动重试不受限；
   - 抓不到时保留占位图，不裂图、不空白、不报错堆积；
   - 批量执行带 420ms 节流，善待公共 API。
6. **入口全铺开**：
   - 首页工具条「⟳ 补封面」（全量批量）；
   - 详情页「⟳ 重拉封面」（单条）；
   - **关联 Bangumi 后自动补封面**（堵住 R5）；
   - 应用启动后小批量静默自愈（每会话最多 6 部，离线自动跳过）。

**为什么有效**：与其逐条猜测某条目来自哪条路径，不如让系统对所有“结果态”统一收敛到“本地 dataURL 封面”这一个终态 —— 无论来源如何，只要 Bangumi 能搜到该作品，封面就会被补齐并持久化；搜不到的条目则稳定保持占位（可辨识、不报错），留待手动处理。
